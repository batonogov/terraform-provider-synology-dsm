## Architecture

Terraform provider for Synology DSM using Plugin Framework. Two layers:

**`internal/client/`** — Synology DSM HTTP API client
- `client.go`: Auth (SYNO.API.Auth v7), session management (SID + SynoToken), `DoAPI()` for GET requests, `DoAPIPost()` for POST requests (SID/SynoToken in query string, other params in body), retry with exponential backoff
- `user.go`, `group.go`, `share.go`, `share_permission.go`, `user_quota.go`, `package.go`, `container_project.go`, `task_scheduler.go`, `event_scheduler.go`: CRUD/lifecycle methods per resource

**`internal/provider/`** — Terraform Plugin Framework wiring
- `provider.go`: Provider schema (host/username/password/insecure), Configure creates client and logs in
- `resource_*.go`: Resources — full CRUD + ImportState
- `datasource_*.go`: Data sources — Read only

Flow: `main.go` → `provider.New(version)` → `Configure()` creates `client.NewClient()` + `Login()` → resources get `*client.Client` via `ProviderData`

## Critical Synology DSM API Details

- **Developed against DSM 7.2.2** (virtual DSM) and DSM 7.3.2 on RS4021xs+ — API behavior may differ on DSM 6.x

- **Most APIs use GET** — user/group operations send params as query string
- **`SYNO.Core.User` update is `method=set`** — there is no `update` method; it answers 103 ("method not exist"). Account state is **not** the `disabled` param (accepted and ignored on DSM 7) but `expired`: `normal` / `now` / a `YYYY/M/D` date. DSM always answers dates without leading zeros regardless of input, so the client normalises to `YYYY-MM-DD`.
- **Shared folder uses POST** — `SYNO.Core.Share` create/update send `shareinfo` as form-encoded POST body. **Update is `method=set`, not `create` with `name_org`** — the latter is rejected with 3301. `share_quota` is written under that name but read back as `quota_value`, and its unit is **gigabytes**. `enable_share_compress`/`enable_share_cow` are creation-time only (a later `set` reports success and changes nothing), and compression requires cow.
- **Task Scheduler is versioned per method** — `SYNO.Core.TaskScheduler` uses version **3** for `list`, **4** for `get`/`create`/`set`, and **2** for `delete`/`run`/`set_enable`. Version 4 on `list` returns nothing usable. `schedule` and `extra` are bare JSON objects inside form values (not JSON-quoted); `name`/`owner`/`real_owner`/`type`/`enable`/`id` are plain values. `real_owner` is a lookup key, not decoration: `get`, `set`, `delete`, and `run` all require it, and only `list`/`get` report it — hence `GetScheduledTask` lists first. The schedule document nests `"version": 4`, and `repeat_date` is `1001`/`1002`/`1003` for daily/weekly/monthly with `date_type: 0` (a plain `0` is rejected on DSM 7). `week_day` is `"0,1,2"` with 0 = Sunday, not a bitmask. `set` replaces the whole task; there is no partial update.
- **Event Scheduler is shaped differently from Task Scheduler** — `SYNO.Core.EventScheduler` is version **1** throughout, is addressed by `task_name` (no numeric id, so rename = replace), has **no** `schedule` or `extra` object (the command is `operation` with `operation_type`, and the notify fields are top level), takes `owner` as a `{uid: name}` JSON map rather than a username, and JSON-quotes its string parameters. `event` is `bootup` or `shutdown`. DSM has no list method here; `SYNO.Core.TaskScheduler.list` returns event tasks mixed in, distinguishable only by having no `id`.
- **`.Root` is a separate API namespace, not a flag** — `SYNO.Core.TaskScheduler.Root` / `SYNO.Core.EventScheduler.Root` are used *instead of* the base namespace when the owner is `root`, for `create`/`set` only, and additionally require `SynoConfirmPWToken` from `SYNO.Core.User.PasswordConfirm` v2 `auth` (POST, param `password`). Reads and deletes always use the base namespace. The token is fetched per call; its lifetime is undocumented. DSM's own client RSA-encrypts the password over plain HTTP through `SYNO.API.Encryption`; this provider sends it plain and warns at plan time instead.
- **`_sid` and `SynoToken` must be in query string for POST requests** — DSM validates session from URL params, not POST body. `DoAPIPost()` handles this by moving them from body to query string.
- **Auth version 7** — `SYNO.API.Auth` version 7 with `enable_syno_token=yes`
- **Session via `_sid`** — Login returns SID, passed as `_sid` query param (no cookies needed with `format=sid`)
- **User home service is asynchronous-capable** — `SYNO.Core.User.Home` `set` is POST. On virtual DSM it completes synchronously (`{"success":true}`), but the API can return a `task_id`; poll `status` with that id until `finish: true`. `location` must be a volume **path** (`/volume1`) — a bare `volume1` gives error 3101. When disabling, send `enable=false` alone; extra fields trigger 3103.
- **`SYNO.FileStation.Upload` is the only multipart API** — `multipart/form-data` POST to `entry.cgi`. The **file part must be written last**: DSM's uploader consumes the stream sequentially and ignores every field after the file content. The destination *name* comes from the multipart filename, the destination *directory* from `path` — and that `path` is a **raw** form value, unlike `SYNO.FileStation.List`/`.Delete`, which take a JSON array of paths. `api`/`version`/`method` are repeated in the query string as well as the body, because DSM dispatches from the URL before parsing the body. Without `overwrite=true` an existing file fails with 414, and a refused upload is reported as `blSkip: true` inside a *successful* envelope
- **Certificates are split across two APIs, and the split is counter-intuitive** — `list`/`set`/`delete` live on `SYNO.Core.Certificate.CRT`, but `import` lives on the parent `SYNO.Core.Certificate`. Picking the wrong one answers 103. All are version 1. **Every certificate call needs `SynoToken` as well as `_sid`**; without it DSM answers 103, which reads like a bad method name. `import` is `multipart/form-data` with `key`/`cert`/`inter_cert` as file parts and `id`/`desc`/`as_default` as text — and unlike File Station the **files come first** and `api`/`version`/`method` are *not* repeated in the body. An empty `id` creates; an existing `id` replaces the material in place and keeps the service bindings (there is no "already exists" error — `import` deduplicates on the caller-supplied id). `CRT.set` wants `id` and `desc` as **JSON-quoted strings** (the same quirk as `SYNO.Docker.Project`) while `as_default` is a raw value. `CRT.delete` takes `ids` as a JSON array. Sources: acme.sh's `deploy/synology_dsm.sh`, the python `synology-api` client, and a captured DSM response in Tailscale's `configure-synology-cert_test.go`
- **`CRT.list` has no `self_signed` field** — DSM marks only its own built-in certificate, with a nested `self_signed_cacrt_info` object. Everything else has to be inferred from `issuer.common_name == subject.common_name`. `subject` and `issuer` are nested objects, not strings; the date fields are `valid_from`/`valid_till` in OpenSSL asctime with a **space-padded day** (`"May  6 00:00:00 2024 GMT"`), always GMT. `isPkg` is the only camelCase key. Several `services[]` fields are absent rather than null when unset
- **Let's Encrypt issuance is synchronous and long-blocking** — `SYNO.Core.Certificate.LetsEncrypt` v1 `create` takes `domain_name`, `email`, `desc` and runs the whole ACME exchange inline. There is **no task id and nothing to poll**. **SANs go into `domain_name` as a `;`-joined list, common name first** — `alt_domain`, `alt_names`, `domain_list`, and `server_url` do not exist, whatever third-party write-ups claim, and the production ACME directory is hardcoded. `as_default` on `create` is unverified, so the provider claims the default with a follow-up `CRT.set`
- **DSM restarts httpd after a certificate import** (`restart_httpd: true` in the response), dropping the connection and refusing the next few requests — `settleCertificate` reads the certificate back through a ~90s budget rather than once
- **No DSM API writes POSIX mode or ownership** — `SYNO.FileStation.Property` `set` accepts `posix`, `mode`, `unix_perm`, `posix_perm`, `permission`, an `owner` object, and any combination of them, answers `{"running":1,"taskid":…}` every time, and changes nothing. `SYNO.Core.ACL` (`get`/`set`/`status`/`stop`, v1 only despite `maxVersion: 2`) manages the **Synology ACL**, not mode bits. `SYNO.FileStation.Property.ACLOwner` exposes `get` only — `set` is 103. `SYNO.FileStation.CreateFolder` ignores a `mode` parameter. The only knob DSM offers is the global `use_unix_default_perm` in `SYNO.FileStation.Settings`. Reading works: `SYNO.FileStation.List` `getinfo` with `additional=["perm","owner"]` returns `perm.posix`, `perm.is_acl_mode` and `owner.{user,group,uid,gid}`. **`perm.posix` is not a bitmask** — DSM prints the octal digits as a decimal number, so 755 means `rwxr-xr-x`; and `perm.acl` describes the *calling session's* rights, not the path's ACL. A shared folder is addressed in File Station by its bare name (`/containers`), never by volume path. (issue #94)
- **`SYNO.FileStation.Download` returns raw bytes, not an envelope** — a failure comes back as JSON instead. A real download is served with `Content-Disposition`, so that header is what distinguishes a file that merely contains JSON from an error
- **`SYNO.Core.Region.NTP` `set` is a whole-object write** — a `set` carrying only `timezone` is rejected with 5701 ("parameter bad"), confirmed on DSM 7.4-90075 (issue #57). The client therefore does read-modify-write and sends `timezone` + `enable_ntp` + `server` together. Two details that are easy to get wrong: the parameter is **`server`, not `ntp_server`** (the symbol table of `lib/SYNO.Core.Region.so` has no such name), and the clock readings `get` returns alongside the config (`date`/`hour`/`minute`/`second`/`now`/`timestamp`) **must not be echoed back** — DSM exports `SYNONtpSet` and `SYNONtpSetWithModifiedTime` as separate entry points, so sending them is the "set the clock manually" path. `enable_ntp` is a mode **string** (`"ntp"`), not a boolean; only the enabled spelling has ever been captured, so the client echoes DSM's own value wherever it can and falls back to `"manual"` only when forced. Whether `set` wants GET or POST is unknown — no public capture exists — so `setRegionNTP` tries POST and falls back to GET on 103/105. `listzone` returns `{"zonedata":[{"value","offset"}]}` and is used to make an unknown-timezone error actionable.
- Error 105 = "session does not have permission" — usually means wrong HTTP method or missing SynoToken
- Error 119 = "SID not found or invalid" — typically means SID not in query string for POST, or session expired. **Also returned by `SYNO.Core.User.Home` when the account is not the built-in `admin`** — hence `doRequestWithRetry` re-logins at most once per call and then surfaces the 119 verbatim
- Error 3101 = "invalid location" for `SYNO.Core.User.Home` (bare volume name instead of a path)
- Error 3103 = "location parameter missing" for `SYNO.Core.User.Home`
- Error 3301 = "share already exists"
- Error 3106 = "user not found" (from `get` method with `additional` param)
- Error 5701 = "parameter bad" for `SYNO.Core.Region.NTP` — an incomplete or unrecognised time-settings payload. DSM renders it as "please sign in to DSM again", which is misleading: the session is fine.
- Error 4151 = `SYNO.Core.AppPortal.ReverseProxy` `entry` missing or not sent as a JSON string (flattening the object into separate params triggers it)
- Error 4154 = a reverse proxy entry with that description already exists
- **Reverse proxy is an undocumented API** — `SYNO.Core.AppPortal.ReverseProxy` v1 (POST). `list` returns `{entries: [...]}`; `create`/`update` take the whole rule as one form value `entry=<json>`; `delete` takes `uuids=<json array>`. `update` targets the entry by the `UUID` inside the payload. Protocol is an **integer**: `0` = HTTP, `1` = HTTPS. There is no name field — the UI's "Description" is `description`, and `UUID` is the identity. Reconstructed from published DSM 7.x captures and independent clients, not verified by this project; source list is at the top of `internal/client/reverse_proxy.go`.
- **Firewall is a whole-profile API, and it is undocumented** — `SYNO.Core.Security.Firewall*` are all version 1 on `entry.cgi` and admin-only. `Firewall get` answers `{"enable_firewall", "profile_name"}`; `Firewall.Profile set` takes the whole profile as compact JSON in `profile` plus `profile_applying=false`, and only rewrites `/usr/syno/etc/firewall.d/*.json` — the change is not live until `Firewall.Profile.Apply start` → poll `status` → `stop`. `profile_applying=true` answers error 117 on DSM 7. Enum values come from Synology's `synofirewall/fwDB.hpp`; see `internal/client/firewall.go`.
- **`Firewall.Profile get` speaks the adapter-keyed shape, with a string policy — CONFIRMED on virtual DSM 7.2.2** (issue #130). The literal response:

  ```
  GET SYNO.Core.Security.Firewall.Profile v1 get&name=default
  {"data":{"global":{"policy":"none","rules":[]},"name":"default"},"success":true}
  ```

  Adapters are **top-level keys** of the profile, each `{"policy": <string>, "rules": [...]}`, with `name` alongside them. `policy` is `none` / `allow` / `drop` as a **string** — note DSM spells FW_POLICY_DROP `drop` while this provider spells the same value `deny`. There is **no `rules` key and no `adapterPolicyMap` key at the top level at all**. The client used to send exactly those two; DSM answered `success: true` and stored nothing, which is the whole of issue #130's silent no-op. The on-disk `{rules, adapterPolicyMap}` shape from `fwDB.hpp` is real but is what `libsynofirewall` writes to `firewall.d/*.json`, not what the webapi shim speaks — the shim (`lib/SYNO.Core.Security.Firewall.so`) translates, and nobody has published its strings, so **both shapes are still accepted and the choice is made from the response, never from a version number**. Also captured: `Profile list` → `{"profile_names":["custom","default"]}`, `Firewall.Adapter list` → `{"adapter_names":["eth0","global","pppoe","vpn","wlan0"]}`, `Firewall.Rules load&adapter=eth0` → `{"policy":"allow","rules":null,"total":0}`, `Firewall.Conf get` → `{"enable_port_check":true}`.
- **A physical DSM 7 answers adapter-keyed *and* repeats the on-disk key names as sibling adapter blocks — so the shape must be read off the values, never off the key names** (issue #130, reopened; hardware capture, adapter `global`, profile `default`, Container Manager installed):

  ```
  GET SYNO.Core.Security.Firewall.Profile v1 get&name=default
  {"data":{"adapterPolicyMap":{"policy":"none","rules":[]},
           "global":{"policy":"none","rules":[]},
           "name":"default",
           "rules":{"policy":"none","rules":[]}},"success":true}
  ```

  `global` is a genuine adapter entry; `adapterPolicyMap` and `rules` carry that **same** `{policy, rules}` object rather than the maps their names promise — the on-disk shape's key names leaking into the adapter-keyed rendering. Neither is an interface name, and no interface can be called either. The first fix keyed the decision on their *presence*, so this NAS was read as on-disk, `policy` and `rules` were parsed as adapter names (which is what the reported `the profile came back with adapter(s) "policy", "rules"` was), and the write went out in a shape this DSM discards with `success: true` — #130 all over again on 0.6.0. Hence `looksLikeFirewallRulesMap` / `looksLikeFirewallPolicyMap` / `looksLikeFirewallAdapterBlock`: the on-disk shape is chosen only when `rules` maps adapter names to **arrays** or `adapterPolicyMap` maps them to **policies**, an adapter block outranks a bare key name, and an empty `{}` falls back to the key because it is the same object in both shapes. The two impostors stay in `raw` and are echoed back untouched. This also retires the two hypotheses the thread was weighing: the account not being the built-in `admin` and the adapter being `ovs_eth0` — the write was discarded because it was the wrong shape, and it was the wrong shape because of the key names.
- **The rule encoding is CONFIRMED, and it is snake_case with string values — ten fields, no more** (issue #130, captured from a physical DSM 7). A rule looks exactly like this, both on the way in and on the way out:

  ```json
  {"enable": true, "log": false, "name": "web",
   "policy": "allow",                    // allow | drop
   "port_group": "custom",               // all | service | custom
   "ports": "443,8000-8100",             // "all" | "ssh,cifs" | "443" | "1234,5678" | "20000:20010"
   "port_direction": "destination",      // destination | src
   "protocol": "tcp",                    // all | tcp | udp | icmp | igmp | gre | esp
   "source_ip": "10.0.0.0/24",           // "all" | addr | "a-b" | "net/prefix" | country code
   "source_ip_group": "netmask"}         // all | ip | ipset | iprange | netmask | geoip
  ```

  Source: DSM's own web client builds this object in `webman/modules/AdminCenter/admin_center.js` (`getPorts`/`getSrc`, and the `adapterRuleStore` field list), and the same names are string literals in the shim `webapi/lib/SYNO.Core.Security.Firewall.so` alongside the `fwPortGroup`/`strPortGroup`, `fwIpGroup`/`strSourceIPGroup`, `fwPolicy`/`strPolicy` converter pairs. Then verified by writing each variant to a NAS and reading it back. **This is why every earlier attempt crashed synoscgi**: the provider sent the *on-disk* names (`ruleIndex`, `ipType`, `ipGroup`, `ipList`, `portGroup`, `portList`, `direct`), which the shim's parser does not know. The two encodings must never be mixed, and `firewall_rule_wire.go` deletes the on-disk keys on the way out for that reason.

  Five behaviours that are each a bug if missed, all confirmed by round trip:
  - **`policy` must be `drop`.** The provider's own spelling `deny` is not rejected — DSM stores the rule with policy `none`, which matches nothing, so a deny rule silently stops denying.
  - **`set` is a MERGE, not a replace.** A profile written without an adapter key leaves that adapter exactly as it was, rules included. Clearing an adapter needs `"rules": []` sent explicitly, and removing an adapter key altogether is impossible through `set` — that needs `Profile delete` + `create`.
  - **DSM normalises empty fields.** `ports: ""` and `port_direction: ""` come back as `"all"` and `"destination"`; write them that way or the read-after-write check sees a mismatch that is not one.
  - **`log` is write-ignored.** It is accepted and always answered `false`. Never manage it, or it plans a diff forever.
  - **A range is `20000:20010` in DSM's UI and `8000-8100` from this provider, and DSM stores whichever it was given.** Both work, so a selector is only re-rendered when it actually changed (`portsUnchanged`/`sourcesUnchanged`) — otherwise a policy write would quietly rewrite every hand-made rule in the profile.
- **The `Profile get` response is rendered from the on-disk `adapterPolicyMap` keys, which is why a corrupted profile shows phantom adapters.** The shim iterates that map and renders one `{policy, rules}` block per key. On the reporting NAS the file held `{"adapterPolicyMap": {"adapterPolicyMap": 2, "global": 2, "rules": 2}}` — DSM had accepted the provider's old on-disk-shaped payload and taken its two top-level keys for interface names. So the "hybrid" response in the issue was self-inflicted, not a DSM variant. A clean profile on the same NAS (`custom`) answered in the plain adapter-keyed shape.
- **Writing a policy in the adapter-keyed shape works.** The policy round trip is confirmed:

  ```
  set profile={"name":"custom","eth0":{"policy":"drop","rules":[]},"global":{"policy":"none","rules":[]}}  -> success
  get name=custom -> {"eth0":{"policy":"drop","rules":[]},"global":{"policy":"none","rules":[]},"name":"custom"}
  ```

  A rule array in the **wrong** encoding crashes synoscgi rather than being rejected: the on-disk object (`policy`/`ipType`/`ipGroup`/`ipList`/`portGroup`/`portList`/`protocol`/`direct`/`ruleIndex`), the string-enum variant two published clients send, a rule carrying only `name`, and even a bare `[{}]` all make DSM answer its **HTML error page** instead of JSON — the request never reaches one. The same happens on `Firewall.Rules save_start`, so the fragile part is the rule parser, not one method. In the correct encoding (see above) a rule array is accepted and stored; the crash was never about rules being present. `SYNO.Core.Security.Firewall.Rules` has exactly four methods (probed one by one; everything else answers 103): `load`, `save_start`, `save_status`, `save_stop` — and `Rules load` is read-only and adapter-scoped, so nothing needs it now that `Profile set` is known to carry rules. **Still do not brute-force encodings against a NAS**: a wrong guess takes the web interface down, and the shape is now known, so there is nothing left to guess at.
- **Two published "clients" for the firewall API are fabricated and must not be used as sources.** `N4S4/synology-api`'s `core_security.py` (added by an AI-assisted PR) invents `Firewall.Rules` `get`/`list`/`set`/`delete` and `Firewall.Geoip.set`, none of which exist in the descriptor, and sends `profile_name=` to `Profile.Apply` where every real implementation sends `name=`. `stevefulme1/ansible-synology-dsm` invents a rule schema that appears in no dump, no binary and no on-disk file. This matters because `N4S4/synology-api` is a trusted source elsewhere in this file.
- **`SYNO.Core.Security.Firewall` `set` — method CONFIRMED, parameters INFERRED, encoding guessed.** The **method name is confirmed**: DSM's own webapi descriptor for this API lists exactly `{set, get}` on version 1, `authLevel: 1`, `allowUser: admin.*`, `lib/SYNO.Core.Security.Firewall.so` (dumped in LeoMartinDev/synology-api `definitions.6.x.json`; that dump independently reproduces five quirks this file already records — no `SYNO.Core.User.update`, Share updating via `set`, ReverseProxy using `update`, Region.NTP's method list, `Firewall.Rules` having no `get`/`set`). So **there is no alternative method worth trying** — `save`, `set_enable` and friends do not exist, and a 103 here is a real finding. The **object is confirmed to have exactly two fields**: Synology's `synofirewall/synoFW.hpp` models global state as a status flag plus a profile name, on disk as `status`/`profile` in `firewall.d/firewall_settings.json`. The **parameter names on the write** (`enable_firewall`, `profile_name`) are inferred from `get`'s response and corroborated by the only published implementation of the write, an Ansible deployment against DSM 7.2.2/7.3 (KastnerRG/krg-infra `apply_security.py`), which also reports that DSM's settings APIs answer **2001** to a partial `set` — hence the whole-object write. Two things remain guesses and each has a fallback rather than a bet: `setFirewallSwitch` tries POST then GET (103/105), and retries with `profile_name` **JSON-quoted** on 120/2001/5701, because DSM is inconsistent about quoting across APIs and that one implementation quotes it. Pinned by `TestClient_SetFirewall_EnablePayload` and `TestClient_SetFirewall_RetriesQuotedProfileName`.
- **`SYNO.Core.Security.Firewall.Profile` `list` answers `{profile_names: [...]}`** — not used yet, but it is the `listzone` equivalent for making an unknown-profile error actionable. From the same descriptor dump plus NielsKrijnen/SynologyNAS's typings.
- **The DSM 6.x webapi descriptor contradicts one thing this file says about the Event Scheduler.** It lists `SYNO.Core.EventScheduler` v1 as `[list, list_relate, set_enable, delete, run, get, set, create, result_list, result_get_file, config_set, config_get, event_list]` — i.e. there **is** a `list`, contrary to the note above that says DSM has none here and that event tasks must be picked out of `TaskScheduler.list` by having no `id`. Unverified on DSM 7 and deliberately not acted on; worth a probe before anyone builds on the current workaround.
- **The default policy is `adapterPolicyMap`, and it is per adapter — there is no profile-wide one.** `allow`=0, `drop`=1, `none`=2 (`FW_POLICY` in `fwDB.hpp`). `global` is a pre-table rather than an interface and carries `none`. This is why `dsm_firewall.default_policy` is a **map** keyed by adapter rather than a scalar: DSM's own firewall page asks the "Allow access / Deny access" question separately per interface, and a scalar attribute would be a claim about DSM that is not true. The provider spells `drop` as `deny` so it reads the same as a rule action, and refuses the DSM spelling in config so the two cannot drift.
- The **55xx family belongs to certificates**: 5510-5519 and 5534 are import failures (5514 = key does not match the certificate, 5517 = chain does not verify), 5520-5530 are Let's Encrypt failures (5521 = domain validation failed / port 80 unreachable, 5524 = rate limit, 5529 = not publicly resolvable). Wording extracted from DSM's own webman i18n strings by two independent clients; 5510/5512/5517 additionally confirmed by acme.sh bug reports

## Client patterns

- **Share mutations are serialised and retried** — DSM processes `SYNO.Core.Share` create/update/delete one at a time: overlapping calls answer 3328, and a call issued while an earlier mutation is still settling answers 3300. `shareMu` queues mutations client-side and `mutateShare` retries those two codes with exponential backoff (~15s budget); reads stay outside the lock. Permanent answers such as 3301 are never retried.
- **Error codes are the contract, messages are presentation** — `internal/client/errors.go` renders a DSM code as a sentence (`a share with this name already exists (code 3301)`) using a common table plus per-API overrides, because codes above 3000 mean different things in different APIs. `executeRequest` tags each `*APIError` with the API it came from. Never match on the rendered text: use `client.IsAPIError(err, codes...)`. Only add a description for a code whose meaning was verified against real DSM.

- **User fields DSM will not round-trip** — `cannot_chg_passwd` and `allow_ip` are accepted by `set` but never returned by `list`; `passwd_never_expire` is ignored outright. All three are left out of the schema. Per-user IP restrictions on DSM 7 live in the firewall (`SYNO.Core.Security.Firewall.*`), not the account.
- **User `get` returns minimal data without `additional`** — only `name` and `uid`. To get `description`, `email`, `disabled`, `groups` use `list` method with `additional=["description","email","disabled","groups"]` and filter by name.
- **`get` API returns arrays** — `SYNO.Core.User.get` returns `{users: [...]}`, `SYNO.Core.Group.get` returns `{groups: [...]}` — not a bare object. `parseUser`/`parseGroup` must unpack the array wrapper first.
- **Simple resources** (user, group): all CRUD via `DoAPI()` (GET). Delete sends name as JSON array.
- **Packages**: installed state comes from `SYNO.Core.Package.list` v2 with lifecycle fields nested under `additional`. Installation follows Package Center's queue flow (`SYNO.Core.Package.Server.list` → `SYNO.Core.Package.Installation.get_queue` → `install` → poll); start/stop uses `SYNO.Core.Package.Control`. Package removal is opt-in in the Terraform resource.
- **Container Manager projects**: `SYNO.Docker.Project` v1 uses POST and returns `list` as an object keyed by project UUID. Creation follows DSM's sequence: create the directory with `SYNO.FileStation.CreateFolder` → create an empty project → `update` the raw compose content → `build` → optional `start`. `name`, `share_path`, and `get_share_info.path` are JSON-quoted strings; `update.content` and direct-action `id` are raw form values. Current DSM builds expose direct `build`/`start`/`stop`; the client falls back on error 103 to the older GET streaming variants with a JSON-quoted id. A project `share_path` is a File Station path such as `/containers/s3-storage`, not `/volume1/containers/s3-storage`. Project deletion is opt-in and always sends `preserve_content=true`.

  **`WARNING` is a steady state, not a stage on the way somewhere** — DSM reports it whenever some containers run and some do not, which is where a compose file with a one-shot container lives both while up (the long-lived services run, the init container has exited) and while down (nothing runs, but the exited container is still there). No wait may therefore require WARNING to clear: the status never changes on its own, so the wait can only end at the ten-minute deadline. This has now cost two issues — #69, where "wait for RUNNING" never arrived, and #101, where the fix for #69 made WARNING count as running and thereby broke the *preceding* wait for "not running" after a build. The invariant to keep: a build waits for the status to stop being **transient** (`waitForContainerProjectSettled`), and only an outright `RUNNING` blocks the "stopped" target (`containerProjectReached`). Both directions are covered by tests that fail if either rule is reverted.
- **Certificates**: `internal/client/certificate.go` plus `certificate_pem.go`. The leaf of a PEM bundle is identified **structurally** — the certificate nothing else in the bundle was issued by — not as the first block: `cat chain.pem cert.pem` is common enough, and reading the intermediate as the leaf would report the CA's expiry years out and silently break every alert built on it. `expires_at` is parsed from that leaf's DER with `crypto/x509` whenever the configuration holds a PEM (`dsm_certificate`), and only falls back to DSM's `valid_till` text when there is none (`dsm_certificate_lets_encrypt`, the data source, an imported resource). Destroy re-reads the certificate from DSM — not from state — and refuses while `services` is non-empty, naming the services and the four ways out; `force_destroy` is the opt-out. Rotation goes through `import` with the existing id so the service bindings survive. Per-service binding lives in `dsm_certificate_service` (`SYNO.Core.Certificate.Service` `set`, which wants the whole service object plus the correct `old_id` echoed back).
- **Files**: `internal/client/file.go` carries the two request paths that cannot go through `executeRequest` — a multipart upload and a raw download. Both reuse the backoff and single-re-login policy via `retryFileTransfer`. `GetFileInfo` must inspect the per-entry `code` in a *successful* getinfo response, because DSM reports a missing path that way as well as through a failed envelope. `dsm_file` reads content back on every refresh (that is what makes an out-of-band edit a plan), so transfers are capped at 16 MiB to keep state sane. File Station has no API for a POSIX file mode, hence no `mode` attribute.
- **Shared folder**: create (`method=create`) and update (`method=set`) via `DoAPIPost()` (POST) with `shareinfo` JSON — no `name_org`, which DSM rejects with 3301. Get/list/delete via `DoAPI()` (GET). API returns `enable_recycle_bin` (not `recyclebin`) and `quota_value` (written as `share_quota`).
- **Reverse proxy entries**: mutations run under `reverseProxyMu`. The API is per-entry rather than a whole-list `set`, but DSM keeps every entry in one datastore it rewrites and re-renders into nginx on each change, and `CreateReverseProxy` is a non-atomic list → create → list sequence (DSM's create returns no usable UUID). `TestClient_CreateReverseProxy_Concurrent` models a lost-update-prone datastore and fails without the lock. Updates are layered onto the raw entry DSM returned, so unmodelled fields such as `_key` survive the round trip. `frontend.https.http2` is **inferred** from Synology's `synow3.h` and is only sent when enabled; `ReverseProxy.HTTP2` is a `*bool` so "DSM omitted it" stays distinguishable from "DSM said false".
- **Firewall profile level** (`dsm_firewall`, issues #121 and #123): `SetFirewall` in `internal/client/firewall_settings.go` writes the global switch, the active profile, and the active profile's `adapterPolicyMap` as one guarded operation, under the same `c.mu` the per-rule writes take. Four rules hold it together and each has a test:
  - **The lockout guard changes shape with the transition, because the question does.** While the firewall is already on there is a real before-state and the per-adapter comparison used by the rule path applies (`compareFirewallReachability`). Switching the firewall **on** has no real before-state — with the firewall off every adapter admits everything — so a per-adapter comparison would refuse any profile that denies on any interface, including the one nobody uses, and the guard would be useless on the very change it exists for. There the test is the strong one: refuse only when **no** adapter would admit the session (`provesFirewallLockout`). One reachable adapter is enough, because the provider cannot know which interface its own connection arrives on.
  - **Switching the firewall off is never guarded.** It cannot deny a packet, and a NAS whose active profile denies everything is exactly the state somebody would be trying to escape. `Delete` with `disable_on_destroy` passes both opt-ins for the same reason.
  - **Nothing is written when nothing differs.** An apply makes DSM re-render and reload its iptables chains, which drops live connections; a refresh-and-apply that did that every time would be worse than the problem it solves. `TestClient_SetFirewall_Idempotent` fails if any of the three writes becomes unconditional.
  - **Destroy leaves the firewall on.** `disable_on_destroy` defaults to **false**, the opposite of `dsm_user_home_service`. There the risk is leaving a service switched on; here the undo would *remove* a security control, and a `terraform destroy` that silently opens a NAS to the network is not a default anyone would pick knowingly. The destroy warns that the firewall was left running.

  On the resource side: `profile` is `RequiresReplace` (it is the id), `enabled` is **required** rather than defaulted so switching a firewall on is never implicit, and `ModifyPlan` marks `active_profile` and `default_policy_effective` unknown — which is also what turns an out-of-band profile switch into a plan instead of a refresh-only difference no apply would correct. `Read` refreshes only the adapters already present in `default_policy`, because reporting every adapter DSM has would turn a partial map into a permanent diff.
- **Firewall rules**: `dsm_firewall_rule` manages one rule, but DSM has no per-rule API — every write reads the profile, rewrites `rules[<adapter>]`, and writes and applies the whole profile, all under `c.mu` (same lock as share permissions; without it parallel rules clobber each other). Order **is** the policy: DSM matches top to bottom and the array index is the only priority there is (`ruleIndex` is a max+1 counter, not a sort key), so `priority` is a required argument and Read reports the actual index. Rules round-trip through their original JSON map so GeoIP and service-preset selectors survive a write. Two guards live in the client: a lockout check that replays the profile against the client's own source address (recorded from the transport's dialer) and refuses a change that flips reachability from allowed to denied, and a refusal to leave the active profile empty while the firewall is on.

  **DSM's `success` is not evidence, so every write is read back** (issue #130). `SetFirewallRule` re-reads the profile after the write and requires the rule to be in it with the fields it was written with; `DeleteFirewallRule` requires it to be gone; `SetFirewall` compares the switch and `adapterPolicyMap` with what was asked for. A disagreement is `FirewallNotPersistedError` / `FirewallSettingsNotPersistedError`, never a success. Three details are load-bearing. The check **retries** (`firewallVerifyAttempts`/`firewallVerifyInterval`): a write ends with `Profile.Apply`, which makes DSM re-render its packet filter, and a read landing mid-reload may legitimately answer with the previous profile. It **does not check the position**, because clamping a priority to the end of a short list is normal and Read reports the achieved index. And it runs **before** `rememberFirewallPriority`, for the same reason the record is written after DSM accepts a write rather than before it (see #122 below): a layout DSM discarded must not survive in the client. Selectors are compared through the same encoder that wrote them (`firewallPortFingerprint`/`firewallSourceFingerprint`), so a CIDR stored as address + dotted netmask and read back as a CIDR is not a mismatch, and a selector neither side models is skipped rather than guessed at.

  **A profile is written in the shape it was read in** (`FirewallProfile.shape`, issue #130). The client speaks two: the adapter-keyed one a live DSM 7.2.2 answers with (`{"name": ..., "<adapter>": {"policy": "drop", "rules": []}}`, string policy) and the on-disk one from `fwDB.hpp` (`{rules, adapterPolicyMap}`, integer policy). Which one a response is in is decided from the response — and from the **values, not the key names**: a top-level `rules` whose entries are rule arrays (or an `adapterPolicyMap` whose entries are policies) means the on-disk shape, an adapter block outranks a bare key of either name, and top-level objects carrying `policy`/`rules` mean adapter-keyed. Deciding on the key names alone was the reopening of #130: a physical DSM 7 sends both names as sibling adapter blocks (see the capture above). Never decide from a version number, because the webapi shim that renders the profile is not published and nothing says every build renders it the same way. `toWire` dispatches on the recorded shape; sending the wrong one is the whole of #130, since DSM answers `success: true` to a profile object it does not understand. `parseFirewallRule` reads a rule's `policy` through the same converter as an adapter's, so a string `"drop"` cannot be misread as the default (`allow`) and fool the lockout replay.

  **A rule is rendered in the encoding it was read in** (`firewall_rule_wire.go`). `parseFirewallRule` dispatches on the object — a string `policy`, or a `port_group`/`source_ip_group` key, means the adapter-keyed encoding; integers and `portGroup`/`ipGroup` mean the on-disk one — and the render answers in the same one. Mixing them is what crashed synoscgi for three releases, so `toWireAdapterKeyed` deletes the on-disk keys outright rather than trusting that none survived in `raw`. Two rules keep the render honest: a selector the parser could not model (a service preset, a GeoIP country) is echoed exactly as DSM sent it instead of being replaced by a guess, and a selector that parsed but did not change keeps DSM's own spelling (`portsUnchanged`/`sourcesUnchanged`) so a policy write does not quietly rewrite `20000:20010` into `20000-20010` across somebody's hand-made rules.

  **What is still refused is an entry the parser could not read at all** (`FirewallRuleWriteUnsupportedError`, `unparsedRules`). A profile write replaces the whole rule list from the model, so an entry with no model would simply be absent from the payload — the operator loses a rule and nothing says so. The refusal lives in `toWire`, i.e. in `saveFirewallProfile`, the single choke point every profile write passes through, and it covers the whole profile because a `set` carries every adapter. The tests check `sets == 0`, not just the error type — an error raised after the payload was on the wire has already done the damage.

  **A profile response in neither shape is an error, not an empty profile** (`FirewallProfileShapeError`). Every rule write is read-modify-write, so a response the client fails to recognise used to parse into an empty profile and get written straight back — replacing every rule the operator had with the one being added. The error names the top-level keys DSM actually sent. `FirewallProfile.rulesKeyPresent` separately distinguishes "DSM reported no rules" from "DSM never mentioned rules"; the second points at rules living behind the separate `SYNO.Core.Security.Firewall.Rules` API, and the diagnostic says so.

  **A write lays out the whole adapter list, not just its own rule** (issue #122). `c.firewallRuleOrder` remembers, for the life of the process, the priority every rule this client has written was configured with, and `arrangeFirewallRules` rebuilds the list from that record on every write: managed rules take the lowest free slot at or after their configured priority, rules the provider never wrote keep their relative order and fill what is left. The lock alone is not enough — it prevents lost updates but not the race the issue reported, because Terraform creates independent resources in arbitrary order and placing only the rule at hand clamps it to `min(priority, len(list))`. Rules configured 4,3,2,1,0 and arriving in that order settled as `[0,4,1,3,2]`: silently the wrong policy, since a rule that lands under a deny-all never matches. The layout must therefore be a pure function of (list contents, configured priorities) and never of arrival order; `TestClient_SetFirewallRule_OrderIndependentOfArrival` asserts that over all 120 permutations of five rules and fails if placement goes back to being per-rule. Three consequences worth keeping. Equal priorities are broken by rule name (deterministic, and reported as `FirewallOrderConflict` so a tie is never resolved out of sight). **The record is only written after DSM has accepted the write**: recording it up front makes a *refused* write promote an existing rule from unmanaged to managed, and the next write of any other rule then lays the list out using a position that was never accepted — part of a rejected change arriving later through somebody else's write (`TestClient_SetFirewallRule_RefusedWriteLeavesNoTrace`). And a priority past the end of the list still clamps, because priorities are absolute positions: number them contiguously from 0 per profile and adapter, counting rules created in the DSM UI. That case is reported from **Read**, not from the write — mid-apply the client cannot tell an unreachable priority from one whose neighbours Terraform has not created yet, so warning there would fire on most writes of a normal multi-rule apply, while a refresh has the whole list and no concurrent creates. `GetFirewallRulePlacement` exists to carry the list length out of the profile read the lookup already does; without it the resulting diff would read as drift that another apply settles, and it never settles.
- **Write-only content** (issue #104): `dsm_file` takes `content_wo` / `content_base64_wo` and `dsm_container_project` takes `compose_yaml_wo`, each with a `_wo_version` counter. Four rules hold the design together and each has a test:
  - **The value is read from `req.Config`, never from the plan.** Terraform nulls a write-only attribute out of plan and state; only the configuration carries it, and only during an operation. A value that arrives unknown is *not* content — uploading the empty string would truncate the file — so `fileContentBytes` treats unknown like unset and errors.
  - **`_wo_version` is the marker, not decoration.** It is required with the write-only attribute and rejected without it, precisely so its presence in state can tell Read to keep the content out of state. Without it, "write-only" and "freshly imported" would be indistinguishable, and a refresh would quietly persist the secret it was supposed to protect.
  - **Drift is detected through the checksum of the last write, kept in private state** (`content_checksum` / `compose_checksum`). State holds the checksum of what is *on DSM* (`checksum`, `compose_yaml_checksum`), private state holds the checksum of what this provider last *wrote*; a mismatch means somebody edited it out of band, and `ModifyPlan` turns that into a plan. The compose checksum remembered is the one DSM reports back rather than the one sent — a normalizing DSM would otherwise look like permanent drift.
  - **The decision to write is made once and used twice.** `Update` asks the same `composeWillChange` / `fileContentWillChange` question the plan asked, and only writes the document when the answer is yes. Reading the value out of the configuration merely because it is there would deploy an edit the practitioner deliberately left un-versioned, contradict the checksum the plan carried, and rebuild the containers on the way — which is why `SetContainerProjectRunning` exists: a start or stop must not need a document the caller may not have.
  - **A resource this provider never wrote adopts a baseline on first refresh.** After an import, a `state rm`, or an upgrade from a version without private state there is no reference point, and without one an out-of-band edit would go unnoticed forever. `Read` records the current checksum exactly once — writing it on every refresh would move the goalposts and detect nothing.
  - **`ModifyPlan` marks the attributes an apply rewrites as unknown.** Terraform carries computed attributes forward from prior state, so without it a changed file would plan its old `checksum` and be handed a new one after apply — "provider produced inconsistent result after apply" — and in write-only mode there would be no diff at all. This applies to every attribute the update path rewrites, not just the checksum: `dsm_file` re-reads the POSIX block from File Station, and `dsm_container_project` reports a new `status` and `container_ids` after a rebuild **and** after a plain `running` toggle, which is why the project's `ModifyPlan` reacts to `running` as well as to the compose document.
- **parseX()** helpers use `map[string]interface{}` type assertions, not typed structs — matches the loose DSM API responses.

## Debugging the DSM exchange

Every request and response goes through `tflog.Debug` in `executeRequest`, so `TF_LOG=DEBUG` shows the API, the method, the parameters as sent, the HTTP status, the elapsed time and the response body. This exists because a user could not produce the one artifact needed to diagnose issue #130: the provider was silent about what it sent and what came back, and every wire contract in `internal/client` was reconstructed by somebody who could see the wire.

Two rules hold, and `internal/client/logging_test.go` fails if either is broken:

- **Credentials and session material never reach the log** (`secretParams` in `logging.go`). Passwords are obvious; `_sid`, `SynoToken` and `SynoConfirmPWToken` are the half that is easy to miss and matters as much, because a debug log's whole purpose is to be pasted into an issue and a lifted SID is a working DSM session. Documents — file contents, a private key, a compose project — are summarised by length instead (`bulkParams`): printing them helps nobody diagnose an API contract and is the fastest way to write a private key into a log.
- **Ordinary parameters are logged verbatim.** The parameters this provider gets wrong are the ordinary ones — a JSON-quoted profile name, an adapter key DSM does not keep, a `shareinfo` field accepted and ignored — so redacting broadly to be safe would hide the very bug the log exists to find.

**An HTML body is a crash, not a parse error.** DSM's web server serves its own error page (HTTP 502, on some builds 404) when synoscgi dies mid-request, and `looksLikeHTML` turns that into a sentence saying so. Confirmed against virtual DSM 7.2.2, where any non-empty rule array in a firewall profile does it every time. Reporting it as `invalid character '<'` sent readers after a provider bug that was not there.

## Task execution opt-in

`dsm_scheduled_task` and `dsm_event_task` create DSM tasks that run shell commands, normally as root, which makes write access to a Terraform configuration equivalent to root shell access on the NAS. They are therefore gated behind the provider attribute `allow_task_execution` (default `false`, also readable from `SYNOLOGY_DSM_ALLOW_TASK_EXECUTION`; an explicit `false` in HCL wins over the env var).

- The gate lives in `ModifyPlan`, not `ValidateConfig` — Terraform validates resource config *before* configuring the provider, so `ValidateConfig` cannot see the flag. Failing during plan means a team that leaves it off never reaches apply.
- Destroy is deliberately not gated: removing a task executes nothing, and a configuration that turned the flag back off must still be able to clean up.
- Data sources are never gated: reading a task executes nothing.
- `user` has no default so the privilege is always stated in the open, and `user = "root"` adds a plan-time warning (plus a second warning about the password confirmation when the host is plain HTTP).
- `command` is intentionally **not** `Sensitive` — hiding a root command from plan output removes the only place a reviewer can see what will run.
- `user` is `RequiresReplace` on both resources. The owner selects the API namespace (`.Root` or not), so editing it in place would send the modification to the wrong namespace for the task DSM actually holds.
- The gate is enforced in `ModifyPlan` **and** re-checked in `Create`/`Update`. The duplication is deliberate: a privilege boundary should not rest on one call site, and `resource_task_lifecycle_test.go` fails if either check is removed.

## Task resource hazards worth preserving

Three failure modes here are specific to tasks and each has a regression test in `resource_task_lifecycle_test.go` or the client test files:

- **Never build a client request in argument position.** Go evaluates arguments before the call, so `client.CreateEventTask(ctx, buildRequest(...))` reaches DSM *before* any diagnostic the builder raised can be inspected — creating a root-capable task that no state entry tracks and destroy cannot remove. Build first, check `ok`, then call.
- **A create that succeeds but cannot be read back must still return a task.** `CreateScheduledTask`/`CreateEventTask` return a non-nil task *alongside* an error in that case, and the resources write state before reporting it. Same reason: DSM has already created the thing.
- **`real_owner` is never guessed.** The create path reads back through `GetScheduledTask`, which lists first. Assuming `real_owner == owner` breaks exactly when it matters — a root-owned task created from an admin session — and DSM answers a get with the wrong `real_owner` by returning an empty task, i.e. "not found" for something it just created.

Two smaller invariants: `repeat_until_hour` is a `*int` in the client because unset ("end the window at the start hour") and an explicit `0` are different, and an explicit value earlier than `hour` is rejected rather than rewritten (rewriting produced "provider produced inconsistent result after apply"). And `applyScheduledTaskToModel` takes an `applyMode`: an unrepresentable schedule is an error after a write but only a warning during refresh, because failing on refresh would break every later plan including the destroy that would clean it up.

## Resource implementation pattern

Every resource follows the same structure (see `resource_group.go` as the cleanest reference):

1. `XxxResource` struct with `client *client.Client`
2. `xxxResourceModel` struct with `types.String`/`types.Bool`/etc fields
3. Schema: `id` (computed), required fields with `RequiresReplace` for immutable attrs, optional fields with defaults via `booldefault.StaticBool()`
4. **Read must set ALL state fields** from API response (including `ID` and `Name`) — required for import to work
5. Read uses `state.ID` with fallback to `state.Name` for lookup after import
6. Import: `resource.ImportStatePassthroughID(ctx, path.Root("id"), req, resp)`
7. **Read removes a vanished object from state instead of erroring** — `if removeIfGone(ctx, resp, err, "<kind>") { return }` before the `AddError`. This is Terraform's contract, and both halves of it bite (issue #131)

**"Gone" and "could not ask" are different answers, and Read must not conflate them.** A refresh touches every resource before anything is planned, so a Read that errors on a deleted object aborts the whole plan — including the resources that would have fixed the drift — and the only way out is editing the state file by hand. Removing the resource on any *other* failure is worse: a timeout, an expired session (119), a permission refusal (105) or a malformed request says nothing about whether the object exists, and dropping it from state would plan a re-create of a shared folder or firewall rule that is still there.

The line is drawn in the client, not in the provider. `client.NotFoundError` (`client.IsNotFound`, `errors.As`) is constructed **only where absence is established**: DSM answered, the answer was well formed, and the object was not in it. Never from the rendered message — the code is the contract, the wording is presentation — and never from a code that describes the caller. Every `Err*NotFound` sentinel is a `*NotFoundError`, so `errors.Is(err, client.ErrFileNotFound)` and `client.IsNotFound(err)` both work; `ErrAccessControlProfileNotFound` is deliberately **not** one, because a missing *referenced* object the provider does not own is a configuration error, not drift.

Two APIs have no "no such object" code at all — `SYNO.Core.Share` and `SYNO.Core.Group` — so `GetShare`/`GetGroup` confirm a refused `get` by listing (`absenceConfirmedBy` in `errors.go`). The confirmation runs only when DSM itself answered with an `*APIError`, and a second read that also fails confirms nothing: the original error is returned. Never the other way round.

Resources whose object cannot go missing — `dsm_system_settings`, `dsm_notification_mail`, `dsm_user_home_service`, `dsm_firewall` — are whole-box settings and keep erroring. Data sources always error on absence: there is no state to reconcile.

## Release Flow

Automated via **Release Please + GoReleaser**, split across two workflows so each release PR carries only the delta since the last release (not the whole history):

1. All commits to `main` must use **conventional commits** (`feat:`, `fix:`, `docs:`, `ci:`, `deps:`, `breaking:`)
2. `release-please.yml` (workflow 1) opens/updates the release PR with the changelog and version bump. It runs on `push` to `main` (skipping the release merge commit itself) and `workflow_dispatch`, and only manages the PR — it never tags (`skip-github-release: true`)
3. Merging the release PR triggers `release-publish.yml` (workflow 2) via `pull_request: closed` of a PR labelled **`autorelease: pending`** — the label Release Please puts on a release PR when it opens it. It tags the release and creates a draft GitHub Release (`skip-github-pull-request: true`), imports the Registry GPG key, runs GoReleaser, and verifies the artifacts. **Do not gate this on `autorelease: tagged`**: that label is applied *after* the release exists, which is workflow 2's own output, so a closed-PR event never carries it and every release is silently skipped (this is what left 0.3.0 merged but untagged). Workflow 2 also has `workflow_dispatch` so a release stranded that way can be finished by hand — the merged PR is still labelled `pending`, which is how Release Please finds it
4. After verification it publishes the draft (archives, manifest, checksums, and signature must pass), flips the PR label to `autorelease: published`, then re-runs workflow 1. Because the previous release is now `published`, the next release PR is computed as a delta

```
conventional commits → release PR → merge → tag + draft release → verified signed artifacts → publish → recompute next PR
```

- **A release can only be created while the release commit is still the head of `main`** — `GITHUB_TOKEN` may not create a tag or a release on a commit further back in the history. Measured on this repository, not inferred: a draft release targeting the release commit answers **403 "Resource not accessible by integration"**, the identical call targeting the head answers **201**, and creating the tag ref on that same older commit answers 403 as well. The token had `contents: write` in every case, so the failure reads as a permissions misconfiguration and is not one — chasing scopes, rulesets or repository settings here is wasted effort. The normal flow never meets it, because merging the release PR makes the release commit the head. It bites when anything lands on top before workflow 2 runs — a CI fix, a docs commit. Recovery is the `tag` input on workflow 2: create the tag and a draft release with a **personal** token (which may target an older commit), then run workflow 2 with that tag so GoReleaser fills the existing draft (`use_existing_draft: true`), verifies it and publishes
- **Never create tags manually** — Release Please manages versions
- **Never skip conventional commits** — changelog and versioning depend on them
- Dependabot keeps Go modules and GitHub Actions up to date (weekly, `deps:` / `ci:` prefix)

## CI/CD

- `.github/workflows/test.yml` — unit tests on push/PR
- `.github/workflows/release-please.yml` — opens/updates the release PR only (`skip-github-release`)
- `.github/workflows/release-publish.yml` — tags, signs, verifies, and publishes a release on `pull_request: closed` of a tagged release PR, then recomputes the release PR


**Setup:** Lima VM (`.lima/dsm.yaml`, aarch64 QEMU) → Docker inside VM runs `vdsm/virtual-dsm` container (`docker-compose.test.yml`) → DSM API on `localhost:5001` → `scripts/wait-for-dsm.sh` polls until ready (~10-20 min on cold start, seconds on restart with saved state).

**The image is pinned by digest** (`docker-compose.test.yml`). `vdsm/virtual-dsm` ships a new DSM every few days — 7.51 in May 2026, 7.65 by late August — and this container *is* the system under test, so an unpinned image makes a red run unreadable: "the provider broke" and "DSM changed underneath it" look identical. It also ties the saved Lima state to the image that produced it, so a silent bump costs a cold boot as well. Dependabot watches `docker-compose` weekly, so a new DSM arrives as a reviewable PR with its own acceptance run rather than as a surprise. When bumping by hand, update the tag *and* the digest together — Docker resolves the digest and ignores the tag, so a tag-only edit is a lie in the file.

**In CI the same container needs two overlay files** (issue #128). `vdsm/virtual-dsm` documents `/dev/net/tun` plus `NET_ADMIN` as required and `/dev/kvm` as what keeps it from running at emulation speed, and none of that can live in `docker-compose.test.yml`, which is also used inside the Lima VM where `/dev/kvm` does not exist — Compose resolves `devices` before starting anything, so naming a device the host lacks fails the whole `up`. Hence `docker-compose.ci.yml` (tun, `NET_ADMIN`, runner-sized RAM and cores) and `docker-compose.ci-kvm.yml` (`/dev/kvm` alone), the second layered on only when the runner exposes the device. Without them the container never gives the guest a network, nothing answers on port 5000, and the *only* symptom is `wait-for-dsm.sh` timing out — which is why the workflow now captures `docker compose logs` on failure and puts the tail in the issue it opens. A wait timeout with no QEMU output in that tail is a container problem, not a failing test.

**The acceptance gates are environment variables, never `go test` flags.** `internal/acctest` reads them with `os.Getenv`, so `go test -DSM_ACC_QUOTA=1` exits with "flag provided but not defined" before a single test runs. The names are exactly `DSM_ACC_QUOTA`, `DSM_ACC_CONTAINER_PROJECT`, `DSM_ACC_CONTAINER_IMAGE`, `DSM_ACC_SYSTEM_SETTINGS`, `DSM_ACC_REVERSE_PROXY` and `DSM_ACC_FIREWALL`; there is no `DSM_ACC_FILE`, `DSM_ACC_CONTAINER`, `DSM_ACC_SYSTEM` or `DSM_ACC_TASK`, and the File Station tests are ungated.

**Virtual DSM specifics:**
- Login with empty password (`admin`/`""`)
- No shared folders by default — tests must create them
- No `homes` share — don't reference it in tests
- User quota API returns error 102 — not supported on virtual DSM. The three `dsm_user_quota` acceptance tests skip unless `DSM_ACC_QUOTA=1` is set; run them against real hardware with that env var enabled.
- Container Manager is unavailable on virtual DSM. `dsm_container_project` acceptance tests skip unless `DSM_ACC_CONTAINER_PROJECT=1` and `DSM_ACC_CONTAINER_IMAGE` are set against physical hardware.
- Sessions are short-lived; the client re-authenticates automatically on error 119

**Acceptance tests** (`*_acc_test.go` in repo root):
- `TestAccPreCheck` validates env vars (`TF_ACC`, `SYNOLOGY_DSM_HOST`, `SYNOLOGY_DSM_USERNAME`, `SYNOLOGY_DSM_PASSWORD`)
- `TestAccPreCheckQuota` additionally requires `DSM_ACC_QUOTA=1` (gates the quota tests; `SYNO.Core.Share.Quota` is error 102 on virtual DSM)

- `SYNOLOGY_DSM_PASSWORD` can be empty (supports DSM first-login state)

## Known Issues

- ~~**Test state pollution**~~ — resolved: sweepers in `sweeper_test.go` delete leftovers named `tfacctest*` before a run. Container projects are swept before their backing shared folders; unsupported project APIs are skipped on virtual DSM. `task test-acc` sweeps automatically; `task sweep` runs it standalone. Only the root package registers sweepers, so the command is `go test . -sweep=all` (not `./...`, which fails with "flag provided but not defined").
- ~~**`dsm_user.password` blocks clean import**~~ — resolved: `password` is now `Optional` + `Sensitive`, with `ModifyPlan` requiring it only when the user is actually being created. An imported account can be managed without putting the password in config.
- **Explicit `""` on optional strings** — `nullableString` normalizes empty descriptions/emails to null on Read (fixing the omitted-attribute drift). Setting `description = ""` explicitly still produces a perpetual diff because DSM cannot represent an intentional empty string; see `internal/provider/helpers.go`.
- **Quota untested on hardware** — the quota resource only validates on a real NAS (`DSM_ACC_QUOTA=1`); it is skipped on the virtual DSM.
- **Shared folder fields DSM will not round-trip** — `hide_unreadable` can be written but is never returned by `get`, and `unite_permission` is accepted and ignored. Both are left out of the schema rather than exposed as permanent drift.
- **POSIX mode is reported but cannot be managed** — `dsm_shared_folder`, its data source, and `dsm_file` expose `posix_mode`/`posix_owner`/`posix_group`/`posix_uid`/`posix_gid`/`acl_mode` as computed attributes, filled from File Station `getinfo`. They are read-only because DSM has no API to write them (see the API note above). The practical consequence, reported in issue #94: a shared folder created through DSM lands in ACL mode with mode `000`, which DSM, SMB and File Station honour through the ACL and a Docker bind mount does not — so a container not running as root cannot read the path. Fixing it needs a `chmod` on the NAS. The extra `getinfo` call is best effort: File Station is a package that can be absent, so a failure leaves the attributes null instead of failing the read. Virtual DSM reports 777 everywhere, so the symptom itself can only be reproduced on hardware.
- **Share encryption not implemented** — `encryption` / `encrypt_pwd` plus the `SYNO.Core.Share.Crypto*` family (key management, mount/unmount) need their own design; deliberately out of scope for the extended-attributes work.
- **`personal_photo_enable` is read-only in practice** — `SYNO.Core.User.Home` `set` accepts the parameter and answers `success:true`, but `get` keeps reporting `false` (likely needs the Synology Photos package). It is therefore exposed only on the `dsm_user_home_service` data source, not the resource, to avoid a perpetual diff.
- **User home service needs the built-in `admin`** — other administrator accounts get error 119 from `SYNO.Core.User.Home` even with a valid session.
- **Container projects unverified on hardware** — the wire contract is covered by stateful HTTP tests, but project create/build/start/update/delete acceptance requires compatible physical hardware and a pullable test image.
- **Certificates unverified against a real DSM** — the wire contract is covered by `httptest` and comes from three independent production implementations (acme.sh, python `synology-api`, a captured DSM response in Tailscale's test data), but no call has been made against hardware. The soft spots are: the `import` part ordering (acme.sh's files-first layout is copied verbatim; File Station needs the opposite), whether `CRT.set` tolerates a rename without `as_default`, whether `LetsEncrypt.create` echoes `desc` back into the certificate, and the exact behaviour of the httpd restart after an import. There are no acceptance tests: issuance would spend a real Let's Encrypt rate-limit slot and `SYNO.Core.Certificate` is not expected to work on virtual DSM.
- **The certificate destroy guard trusts `CRT.list` to report service assignments** — it refuses to delete a certificate whose `services` array is non-empty. If some DSM build returns assignments only when asked for them (the way `SYNO.Core.User.get` needs `additional`, in this same project), `services` would arrive empty, the guard would wave the delete through, and the affected services would be left without TLS. Nothing in the captured responses suggests this, and none of the three reference implementations passes an extra parameter here — but it has not been checked on hardware, and it is the one way this guard fails silently rather than loudly. Confirm it on a real NAS by assigning a certificate to a service and checking that `services` is populated in a plain `CRT.list`.
- **`dsm_certificate_lets_encrypt.email` cannot be read back** — DSM does not report the ACME contact address, so it is absent from state after an import and deliberately carries no `RequiresReplace`: an attribute that can never be refreshed must not be able to trigger a destroy. Changing it warns and records the value rather than reissuing.
- **A DSM-side Let's Encrypt renewal may replace the certificate object** rather than update it, invalidating the id in state. `dsm_certificate_lets_encrypt`'s Read falls back to matching the subject common name and adopts the new id, because dropping the resource would make Terraform request another certificate against the rate limit.
- **`dsm_file` unverified against a real DSM** — the multipart upload, the raw download, and the getinfo/delete contracts are covered by `httptest`, and `file_acc_test.go` should run on virtual DSM (File Station is present there), but no acceptance run has happened yet. The wire details came from Synology's File Station API guide, so the per-code hints in `fileErrorDetail` live in the provider layer rather than the client's verified error table.
- **`dsm_system_settings` write path is inferred, not verified** — only `SYNO.Core.Region.NTP` `get` has been captured from hardware (issue #57), plus the negative result that a `timezone`-only `set` answers 5701. The parameter *names* (`timezone`/`enable_ntp`/`server`) come from the DSM library symbol table and the `get` payload; the requirement that all three travel together, the GET/POST verb, and the `enable_ntp` value for the disabled state are all inferences. Reads are ungated; the write acceptance tests skip unless `DSM_ACC_SYSTEM_SETTINGS=1`. Setting `ntp_enabled = false` on a NAS that currently has NTP on emits a Terraform warning because the value is a guess. `SYNO.Core.Region.NTP` also exposes `setzone`/`sync`/`status`/`ensure_ntp_sync_and_enable`; `setzone` is likely the clean timezone-only path but its parameters are undocumented and it is not used.
- **Reverse proxy unverified on hardware** — the wire contract is reconstructed from third-party DSM 7.x captures and covered by unit tests that assert the exact payload, but nothing here has talked to a real DSM. `frontend.https.http2` is the weakest link: the key name comes from Synology's own header, its nesting under `https` is deduction. Acceptance tests are gated behind `DSM_ACC_REVERSE_PROXY=1` because they rewrite live nginx configuration.
- **Access control profiles are out of scope; per-entry certificate binding now exists** — `dsm_certificate_service` binds a certificate to a named DSM service through `SYNO.Core.Certificate.Service`, so an HTTPS reverse proxy source no longer depends on the DSM-wide default. `access_control_profile` still references a profile that must already exist.
- **`dsm_firewall`'s write has never touched a NAS from this repository** — the method name and the two-field object are confirmed from primary sources (see the API note above), but this project has not made the call. The soft spots, in order of how likely they are to bite: whether `profile_name` wants plain or JSON-quoted values (a guess with a retry behind it), whether DSM wants POST or GET (a guess with a fallback behind it), and whether `Firewall set` alone makes a profile switch live or still needs `Profile.Apply` afterwards — the client applies in that case, which is at worst redundant. Acceptance tests are gated behind `DSM_ACC_FIREWALL=1` and deliberately never switch the firewall **on**: the failure mode of getting that wrong is a drive to the building. What they can confirm is that the call is accepted and that the per-adapter policy round-trips — which it now does, in the adapter-keyed shape, on virtual DSM 7.2.2. A capture of the Control Panel's own request would retire this entry outright.
- ~~**The provider will not render a firewall rule into an adapter-keyed profile**~~ — resolved (issue #130). The encoding was read out of DSM's own web client, cross-checked against the shim's string table, and then confirmed by writing every selector variant to a physical DSM 7 and reading each one back. See the rule-encoding note above; the client lives in `internal/client/firewall_rule_wire.go`. What remains refused is only an entry the parser could not read at all, because rewriting the profile would delete it silently.
- **`dsm_firewall_rule` is verified against hardware only for the wire contract, and there are still no acceptance tests** — the encoding, the merge semantics of `set`, and DSM's normalisations were all confirmed by writing to a real NAS and reading back, but into an **inactive** profile with no `Profile.Apply`, so nothing has ever been loaded into a live packet filter from this repository. Two things are therefore still unproven: that an applied profile behaves the way the model says (the lockout replay's whole premise), and the `Profile.Apply` polling loop against a real reload. An acceptance test would have to enable a real firewall on the box running the suite, which is exactly what the resource's guards exist to prevent; it needs a NAS reachable by console first. One smaller unknown: whether `Firewall.Profile get` ever returns the profile nested under a `profile` key (both are accepted; hardware returned it bare).
- **`Profile set` merges, so the provider cannot remove an adapter from a profile** — sending a profile without an adapter key leaves that adapter untouched, rules included. Clearing an adapter's rules works (`"rules": []`), removing the key does not; that needs `Profile delete` + `create`, which the provider does not do. The visible consequence is that an adapter the provider has ever written keeps its entry in `adapterPolicyMap` at the default policy, which is `allow` and therefore indistinguishable in effect from having no entry.
- **Lockout guard sees the local source address** — it uses the local end of the TCP connection to DSM. Behind NAT, DSM sees a different address and the guard can be wrong in both directions. It also cannot replay GeoIP or service-preset rules; those make the check inconclusive, which warns rather than blocks.
- **Task Scheduler wire contract unverified on hardware** — `SYNO.Core.TaskScheduler` and `SYNO.Core.EventScheduler` are undocumented. The encoding was transcribed from three agreeing implementations (python `synology-api`, `synology-community/go-synology`, 007revad's `task_setup.sh`, the last with real DS218/DSM 7 findings) and is covered by request-asserting httptest cases, but nothing has been run against a NAS from this repository. The parts that are inference rather than transcription are flagged `INFERRED` in the client: `limit=-1` on `list`, and the assumption that event tasks are the list entries carrying no `id`. `SYNO.Core.EventScheduler.get` in particular has no captured real response anywhere, so `parseEventTask` accepts both `task_name`/`name` and `operation`/`script`. There are no acceptance tests for either resource yet.
- **One-shot scheduled tasks are not modelled** — DSM's `date_type: 1` schedules (a single date, yearly, every 3/6 months) are deliberately unsupported: a fixed past date is not an ongoing desired state. Reading such a task yields an empty `Frequency`, which the resource reports as an error and the data source surfaces as null rather than guessing.

## Roadmap

Remaining gaps: a `dsm_group_member` resource for atomic membership, per-share NFS rules (`SYNO.Core.FileServ.NFS.SharePrivilege`) and the global protocol services (`SYNO.Core.FileServ.SMB`/`NFS`/`FTP`), and share encryption. Reverse proxy is implemented (`dsm_reverse_proxy`); access control profiles themselves (`SYNO.Core.AppPortal.AccessControl` create/update/delete) are still read-only here. Certificates are implemented, including per-service binding (`dsm_certificate`, `dsm_certificate_lets_encrypt`, `dsm_certificate_service`). Then: Synology Drive → Photos.

**Provider scope is documented, not implicit** (issue #124). `templates/index.md.tmpl` — and therefore `docs/index.md` — carries a "Scope" section that sorts every gap into three bins: not implemented yet (contributions welcome), not expressible through the DSM API at all (POSIX mode, fields DSM never returns, one-shot task schedules), and the NAS's own network configuration. The distinction is the point: a reader with a bootstrap checklist has to be able to tell "nobody has written it" from "DSM offers no API for it". Keep the section in step with `Resources()` when a resource lands.

**The NAS's own network settings are not implemented, and the reason is a hazard, not a preference.** `SYNO.API.Info` on virtual DSM 7.2.2 lists `SYNO.Core.Network` (v1–2), `SYNO.Core.Network.Ethernet` (v1–2), `SYNO.Core.Network.Interface`, `SYNO.Core.Network.Bond`, `SYNO.Core.Network.Router.Gateway.List` and `SYNO.Core.Network.Router.Static.Route`, so the namespaces exist. Published dumps of DSM's API definitions (`kwent/syno`) add the method names: only `SYNO.Core.Network` (`get`/`set`/`test_internet`) and `SYNO.Core.Network.Ethernet` (`get`/`list`/`set`) write anything — **`SYNO.Core.Network.Interface` is `list`-only**, so it is not the static-IP path however often it is named as one, and `SYNO.Core.Network.DNSResolve` does not exist at all. What is missing is the payload: the dumps carry method names and never parameters, and no public client writes these APIs. The python `synology-api` calls `SYNO.Core.Network` with `get` only (`core_sys_info.py`) and its `core_network.py` covers `set` only for IPv6, MAC clone, static routes, WOL and traffic control; `synology-community/go-synology` declares only `NetworkGet`; the other Terraform provider for DSM ships `synology_core_network` as a data source. The multi-source reconciliation that produced the reverse proxy and firewall clients has no material to work with here. The blocker on top of that is structural: an apply that moves the address severs the session that would confirm it, so the provider cannot distinguish success from a NAS that fell off the network, and recovery is physical. A resource here needs (1) a lockout-style plan-time check on the model of `firewall_lockout.go`, (2) a reconnect-and-confirm path at the *new* address with a bounded budget, (3) whole-object read-modify-write, as `SYNO.Core.Region.NTP` already forces, and (4) the wire contract captured from hardware, including which of the two writable namespaces the UI uses and what the interface is actually called (Open vSwitch makes it `ovs_eth0`, not `eth0`). Do not ship it on inference alone.
